## 一、看图诊断：先五问，再检查

### A. Shore 五问（主，必须有答案）

1. **视点**：相机在哪、视高、朝向？哪些平面关系完全由机位决定（后期改不了）？
2. **边界**：这张图是「框=终点」（主体明确，框只是收尾）还是
   「框=起点」（边界本身就是结构，从边界往内建构）？四边各排除了什么？
3. **平面关系**：前景 / 中景 / 背景在**二维平面**上的对位与间隔，哪些是承重骨架？
   裁掉某元素会不会同时切断它和别的东西的对位？
4. **注意力路径**：眼睛从哪进、经过哪几个点、能往深处走多远？有没有多个可读点？
   候选裁剪是**延长**还是**截短**了这条路径？
5. **透明性**：这个决策会不会显得「很用力」？有没有为了干净 / 突出主体而破坏语境？

答不出来就说不确定，请用户指出想看什么，不要编点评。

### B. 技术检查（次，逐项过一遍）

- **边缘扫描**：沿四条边走一圈，记录被「半个」切进来的物体（半个人、半个瓶子、
  露出一半的车）。**但先判断它是不是结构的一部分** —— Shore 式构图里，
  边缘元素常常是与背景对位的关键，不能一律当杂物清掉。
- **线条**：地平线是否水平、建筑竖线是否垂直、有无引导线。
- **留白方向**：视线 / 运动前方要留空间。
- **比例与取舍**：当前比例适合用途吗？裁掉的部分有无不可替代的信息？
- **光与色（只诊断，不修）**：欠曝 / 过曝 / 偏色 / 发灰。
  本 skill 不调色；若问题严重，建议用户先去 darktable / Lightroom 显影。

## 二、二次构图规则

### 优先顺序（Shore 版；冲突时按此排序）

1. **不缩短注意力路径** —— 优先保住能让观者往画面深处走的平面关系
2. **不切断平面上的对位关系** —— 前景与背景在二维平面上的呼应
3. 不切主体关键部位（眼睛、关节、建筑顶端与塔尖）
4. 边缘半截物体：先判断是干扰还是结构，再决定清或留
5. 地平线 / 竖线端正（对称倒影构图除外，此时居中是合理的）
6. 符合目标用途比例
7. 三分线 / 黄金分割 —— **只是描述工具，排最后**

> 三分法是启发式，不是定律。中心构图、对称构图、大量负空间都合法。
> 消失点居中时，对称本身就是注意力通道，**别硬掰到三分线**。
> 若所有候选都缩短注意力路径，正确结论是「**回到原框，但把冗余切掉**」——
> 不是「不裁」。两条都做不到时，交付原图并说明原因，同时**明确告知这是例外**，
> 不要让它变成默认（v1.5.0）。

## 四、切边落点（v1.5.0 新增，实战教训）

**切边必须压在客观存在的结构线上，不能压在内容中间。**

| 可以切 | 不要切 |
|---|---|
| 楼层分隔带、檐口、窗台线、柱中线 | 从一排窗户中间横穿 |
| 重复的窗格、重复的路面纹理 | 把招牌、门牌、人物、转角弧线切成两半 |
| 天空与地面这种「无信息带」 | 半棵树、半辆车、半个人 |

原因：切在结构线上，观者读成「画面到此为止」；切在内容中间，观者读成
「照片被裁坏了」——**观众的注意力会被切口吸走，这正是 Shore 说的不透明**。

**定位方法（不要靠目测猜）**：v1.6.0 起由 `survey` 直接给出结构线位置，
不要再手写亮度剖面脚本：

```bash
python3 scripts/photo_lab.py survey "/path/IMG.DNG"   # → structure_lines
```

`structure_lines` 给的是「行/列方向的局部细节能量峰」做 NMS 后的位置（源像素），
天然对应石带、檐口、窗台这类横向结构。实战数据（IMG_0862，预览 1800×1350）：

| 顶边 y | 结果 |
|---|---|
| 150 / 250 / 330 | 横穿窗框，失败 |
| **300** | 落在窗户上方的石头浮雕带，干净 |
| 420+ | 丢掉招牌，失败 |

代价：顶边从 150 降到 300 会多丢约 11% 的画幅高度，
但换来一个读得通的边界——**宁可多切，也不要切脏**。

## 五、旋转判定（v1.5.0 新增）

旋转有两个完全不同的用途，必须分开：

1. **矫正（默认允许）**：画面存在滚转误差时转到 0°。
   判定方法：看细长垂直线（灯柱、窗框、墙角）与左右边框的夹角。
   **<0.3° 一律当 0°**；0.3°–3° 用 `--rotate` 反向矫正。
2. **风格化（必须用户明确要求）**：故意让水平/垂直线与边框成角，制造张力。
   代价是观者先看到「照片歪了」而不是内容，**透明性受损**。

**先分清「滚转」和「透视」**：广角仰拍会让楼体上小下大（keystone），
竖线向一点汇聚——这**不是**旋转，旋转只会让汇聚轴歪掉，越修越糟。
keystone 只能靠透视矫正（本 skill 不做），或拍摄时保持机背平行。

### 怎么把角度量出来（v1.5.1：可复现方法）

靠肉眼看缩略图判断 ±1° 是不可靠的，会来回改。**用单条线的连续性追踪**
（不是锐度法，见下面的坑）：

```python
# 从 (sx, sy) 出发向右逐列跟随同一条暗缝，斜率即滚转角
def trace(sx, sy, ex, win=3):
    y = sy; pts = [(sx, sy)]
    for x in range(sx+1, ex):
        best = min((px[x, yy], yy) for yy in range(y-win, y+win+1))
        y = best[1]; pts.append((x, y))
    return pts
# 对 pts 做最小二乘拟合 → slope → math.degrees(math.atan(slope))
```

判据：**残差 < 1.5px 才算测到**，否则说明跟丢了（线条断、纹理弱），换起点重来。
多取 4–5 条线，斜率一致才可信。

**四个坑（前三个在 IMG_0896 上踩过，第四个在「我与黄浦江」上踩过）**：

1. **锐度法（找「行平均亮度梯度最大」的角度）在周期纹理上会混叠**：
   同一张图天花板格栅给出 2.0°、整幅给出 1.25°，互相矛盾，作废。
2. **逐列取最暗点再拟合会跳线**：地砖缝拟合残差 12px，三种缝给出
   -0.05°/-0.39°/+0.13°，看着都像「0°」，实际是被噪声骗了。
3. **别拿弧线当直线**：天花板与墙面的交线在一点透视里是曲线，
   拟合残差 19px，测出来的是几何形状不是歪斜。
4. **近景横线不是水平线，是透视线**：栏杆、江岸、马路牙子都是向远方
   收敛的 3D 直线，成像后**必然斜**，斜度是透视不是滚转。同样的
   RANSAC 拟合：「我与黄浦江」红栏杆上沿 +8.8°、白栏板上沿 +8.5°、
   江岸水线在同一 y 带不同 x 区间给出 +2.6° 与 +0.05°（自相矛盾）。
   全部作废——**近景横线只能用来判「结构线在哪」，不能用来判滚转**。

### 竖边验滚转（建筑 / 城市夜景首选，v1.5.2；v1.6.0 起由 `level` 执行）

**竖直线才是干净的判据**：滚转会让画面里**所有**竖边朝同一方向倾同样的角度，
而俯仰造成的 keystone 是左右对称的（左边外倾、右边外倾）。所以取三条以上
分布在不同 x 的竖边（塔身、楼角、窗框），拟合向竖直方向的斜率：

```bash
# v1.6.0：不要再手写这段测量代码，直接跑
python3 scripts/photo_lab.py level "/path/IMG.DNG"
```

`level` 内部走 **Hough 投票**而不是「逐列找最暗点 + 连续追踪」：
在内容带内按 `(angle, offset)` 累加，越界票**丢弃**（不能 clip，否则陡线会被
灌进边界 bin，manufacture 出一个恰好等于 `±max_deg` 的假峰），再 NMS 取峰。
贪心追踪在夜景会跳线——每行窗口里有多个竖边，内点率掉到 6–7% 仍会返回一个
「看起来合理」的角度，这是它最危险的地方。

判读规则不变：三条以上竖边同号同量 → 真滚转；异号或近零 → 无滚转，斜的是透视。
`confidence: high` 要求 ≥ `max(3, 40%)` 条在 0.3° 内一致；`none` 时如实说测不出来，
才回退到「单线连续性追踪 + 残差 <1.5px」的老办法。

> **v1.6.1 新增：单侧证据不算证据。** 印竖边必须横跨画面 ≥35% 宽度、左右各有
> 至少一条，否则降为 `low` 并返回 `roll_deg: null`。IMG_0764（外滩望东方明珠）
> 实测：12 条「竖边」全落在 x 16–22% 的紫楼同一面立面，一致读到 −1.80°，
> 一致性检查完全通过——但那是**同一面墙被检出了 12 次**。仰拍高楼时该楼的
> 竖边必然倾斜，倾角随它离光轴的距离增大，这是 keystone，与相机滚转无关。
> 独立交叉检验：该图远场横线（y 77–81%）读 **0.0°**，只有近场街面线读到 −1.8°，
> 与「未滚转 + 近景线带透视」完全吻合。**结论 0°。**
> 教训：「12/12 一致」这句话，在看到它们来自画面的同一个 6% 之前，是骗人的。

实战：「我与黄浦江」（竖幅夜拍）12 条竖边全部读 0.00°（东方明珠塔身右缘、
双子塔左缘、右侧楼多条竖边），`verdict: 12/12 agree at +0.00 deg`；
而同一张图的近景横线给出 +8.8°。**结论 0°，不转。**

> 分辨率提醒：span 只有 70–80px 的线**测不出 1° 以下的角**（0.1° 在 70px 上
> 只有 0.12px）。短基线的高精度小数是噪声，不要拿它当证据。

实战结果对照：

| 照片 | 测法 | 结论 |
|---|---|---|
| `IMG_0862`（街角建筑） | 灯柱/墙体竖线与边框比 → 肉眼 ±2° 明显歪 | **0°**，不转 |
| `IMG_0896`（地铁通道） | 5 条天花板格栅连续追踪，斜率 −2.16…−2.54°，残差 <1.2px | **顺时针 2.2°** |
| `我与黄浦江`（竖幅夜景） | 12 条建筑竖边（Hough 投票，`level`），全部 0.00° | **0°**，不转 |

同一天两张图结论相反，说明**不能设默认角度，只能设默认方法**。
IMG_0896 校正后 `kept_fraction = 0.951`，即旋转吃掉 4.9% 像素，可接受。

> 轻微汇聚（同一格栅从左端 2.48° 渐变到右端 2.16°）说明还有一点 yaw，
> 那是透视问题，转正是唯一能做的一半；不要为了消掉汇聚继续加大角度。

## 六、锚点含义（脚本 `--anchor`，纯技术参考）

**命名指的是「主体最终落在哪」，不是「框往哪挪」** —— 框往右挪，居中的主体才会落到左三分线。

| 锚点 | 框的位置 | 主体结果 |
|---|---|---|
| `center` | 居中 | 居中 |
| `third-left` | 框偏右 | 主体落到左三分线附近 |
| `third-right` | 框偏左 | 主体落到右三分线附近 |
| `top` | 框贴上边 | 保留上部（留天空） |
| `bottom` | 框贴下边 | 保留下部（留前景） |
| `golden` | 框按 0.382 定位 | 居中主体落到 0.618 黄金线 |

> **限制一**：锚点全部基于「主体大致居中」的几何假设，脚本**不做主体识别**。
> 必须看图筛掉切断主体的方案。
>
> **限制二（v1.2.1）**：最大内接框只在一个轴上有余量。竖幅且宽度受限时 `dx=0`，
> 三个水平锚点算出**同一个框**，旧版会静默输出三张相同图。现在脚本会在
> `duplicate_crops` 里点名并标 `anchor_effective: false`。解法：
> `candidates --zoom 0.9` 腾出余量，或干脆用 `candidates --crops` 手写边界。
>
> **推荐做法**：看图后用 `candidates --crops "label:x,y,w,h;..."` 写显式框，
> 再用 `map-crop` 把预览坐标换算到原图，最后 `crop-plan --crop "x,y,w,h"` 落地。
> 这符合 Shore 的「先定注意力路径，再倒推边界」，也绕开所有锚点假设。
> 注意 `--ratio + --anchor center` 会把余量上下均分，**不等于**只裁上方天空。
>
> **限制三（v1.5.2，竖幅尤其致命）**：**同比例的最大内接框在竖幅里就等于原框**。
> 3:4 的竖图再裁 3:4，`dx=dy=0`，不存在「不动就能换构图」的选项；
> 想要任何取景变化，必须同时缩小宽与高（`--zoom` <1 或显式框）。
> 而如果水平方向已被 "A 在左、B 在右" 锁死（本例：塔左缘 12.5%、人物头右缘 77%），
> 可裁幅度就只有 100px 级，**上下两端往往只能保一个**。
> 先把「可裁预算」算出来再谈审美，否则会做出一个几何上不存在的方案。

### 禁忌

- 不切关节、眼线、建筑顶端与塔尖。
- 不为凑比例把主体缩得过小；比例默认锁死，靠收紧取景解决，不靠换比例。
- 一张图里不要同时追求「三分法 + 中心对称 + 大面积留白」，会互相打架。
- **不要为了「画面干净」清掉全部环境信息** —— 平凡场景的价值在关系密度
  （Shore：pay attention to the average moments, not just the dramatic moments）。

### 按题材的额外规则

| 题材 | 要点 |
|---|---|
| 风光 / 地理景观 | 地平线水平；前景留一块视觉锚点；判断注意力能否从前景走到远景 |
| 人像 | 眼睛位置、不在关节处裁；视线方向留白；**注意背景与人在平面上的对位** |
| 街拍 / 环境 | 多为「框=起点」，边界即结构：切就切在结构线上，别切在人和招牌中间 |
| 建筑 / 一点透视 | 对称就大胆居中；消失点是注意力通道，**裁上下会缩短通道**，优先保住纵深出口 |
| 静物 / 美食 | 主体占比高；桌面水平线要正；留出环境的一角增加现场感 |

## 三、候选评估（给 2–3 个候选时用）

**不打分、不加总分。** Shore 反对把 stylization / 公式强加给作品
（见 `shore-first-principles.md` §4）；一个总分会让「哪张更好」看起来像可计算的，
而实际上它取决于观者想注意什么。旧版的 0–2 分表已撤除。

改成逐候选回答五个是否：

- 注意力路径：**延长还是截短**了？眼睛还能往画面深处走吗？
- 平面关系：前景 / 中景 / 背景的**对位骨架**有没有被切断？
- 边界判断：这张是「框=终点」还是「框=起点」？这一刀符合它的框类型吗？
- 语境 / 透明性：有没有为「干净 / 突出主体」清掉环境，显得很用力？
- 用途匹配：比例是否真的匹配用途，还是仅为凑比例而裁？

向用户呈现时，每个候选必须写：
**为什么这样裁 + 牺牲了什么 + 对注意力路径的影响**。
并允许给出「都不如不裁」的结论 —— 这是合法且常见的答案。

## 四、为什么本 skill 不做调色（v1.2.0）

原「调色规则 / 预设 / 参数表」整节已删除。理由：

- 用户要求移除调色模块，改为纯构图 / 无损路线。
- Shore 的「透明性」：*"Structure is not art sauce poured on top of content"*，
  以及 *"err on the side of transparency ... decisions don't call attention to themselves"*
  （Jeu de Paume 大师课公开转录，二手来源）。重风格化与之相悖。
- 工程上：调色是逐像素改写，与「原数据无损 / 非破坏性」目标冲突；
  把它留在默认流程里会让「无损」承诺不成立。

若用户主动要调色：**直接说明本 skill 不做**，并给 darktable / Lightroom 路径。
脚本里 `grade()` 与 `presets` 仅作 legacy 保留，需显式 `--grade` 才生效，
不写进工作流、不主动提议。

## 五、输出与可复现（非破坏性优先）

- **默认**：`crop-plan` 输出 `crop.json`（像素坐标 + 0–1 归一化坐标 + 比例），
  `xmp-crop` 输出标准 `crs:` XMP sidecar。**原 DNG 一个字节不写。**
- **方向（v1.2.1）**：所有坐标以 DISPLAY 方向为准。`info` / `crop.json` /
  XMP 结果都会带 `orientation`、`raw_stored_size`、`coordinate_system`。
  遇到 90° 方向 RAW（如 Orientation=6），务必提醒用户核对编辑器是否按同一
  口径解释 `crs:` crop 值 —— 本机未装 Lightroom / ACR，未验证。
- 需要实体成片时优先 `.png` / `.tiff`（无损压缩），`.jpg` q92 仅用于分享。
- 每次 `develop` 写同名 `.json` sidecar 记录裁剪框，便于批量套用。
- 整条链路 8-bit：无损 ≠ 16-bit；要 RAW 宽容度请先在 darktable 显影。
- XMP 兼容性未在 Lightroom / ACR 实测，必须如实告知用户自行验证；
  不认时退回 `crop.json` 的像素坐标手动裁。
- 批量时先在一张代表图上定参数，再套全组，最后抽查 2–3 张。
