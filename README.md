# Photo Master Eye

**摄影眼二次构图（Photographer's-eye reframing）—— 按 Stephen Shore 的第一性原理判断该裁哪里，而不是套三分法打分表。**

给一张已有的照片，它回答三个问题：**这张画的注意力是怎么走的、边界该落在哪条结构线上、框该不该转**。然后真的出片。

> 不做生成、不做扩图、不做调色。只做一件事：在**不改变长宽比**的前提下重新取景。

---

## 它反对什么

市面上的"智能裁剪"基本是**主体检测 + 三分法**：找到人脸/主体，摆到三分线上，完事。

这套逻辑有三个硬伤：

1. **三分法只是描述工具，不是目标。** 消失点居中时，对称本身就是注意力通道，硬掰到三分线是把照片改坏。
2. **主体检测不知道边界该落在哪。** 切在一排窗户中间，还是切在窗户上方的石头浮雕带上，差别是"照片被裁坏了"和"画面到此为止"——这跟主体位置无关，跟**结构线**有关。
3. **它从不算角度。** 靠眼睛估"好像有点歪"，然后转 1°、2°，常常把本来正的画面转歪。

所以这个 skill 换了一套判据：Shore 讲的**视点 / 边界 / 平面关系 / 注意力路径 / 透明性**，加上**逐像素量出来的结构线**。

---

## 四条默认规则

| 规则 | 含义 |
|---|---|
| **比例锁死** | 原图 3:4 就出 3:4。不换 16:9 / 1:1 / 4:5，除非当次明确指定 |
| **取景必做** | 成品与原图**逐像素一致 = 失败**。必须真的重切、重定位、必要时校旋转 |
| **原片不动** | 原 DNG / RAW **一个字节都不写**。只有真裁了才写 `crop.json` / XMP sidecar |
| **成品在旁** | 写 `<原文件名>_final.<ext>`，与原图**同目录**，不建 `_out/` 子目录 |

过程产物（预览、网格、候选拼图、解码稿、对比图）全部进系统临时目录 `$TMPDIR/pme_work_<stem>/`，任务结束自动清理，只留原图 + 成品。

## 安装

```bash
git clone https://github.com/<you>/photo-master-eye.git \
  ~/.workbuddy/skills/photo-master-eye
```

放在任何支持 `SKILL.md` 约定的 agent skills 目录下都能用。依赖：

```bash
python3 -m pip install --user pillow numpy
# RAW 解码依赖 macOS 自带的 sips（无需安装）。非 RAW 格式不需要它。
```

**平台支持**：JPEG / PNG / TIFF / HEIC 在 macOS、Windows、Linux 上功能一致（走 Pillow）。**只有 RAW 依赖 macOS `sips`**——Windows 上处理 RAW 会给出明确报错，绕过方式是先导出一张 JPEG/TIFF 再处理。v1.6.2 修复了此前「Windows 上连普通 JPEG 都出不了片」的问题。

`numpy` 只有 `survey` / `level` / `panels` 三个分析命令需要；`finish` / `candidates` 等像素命令只依赖 Pillow。

## 工作流

```
survey → level → candidates --crops-src --annotate → finish --crop → compare
```

| 步骤 | 命令 | 拿到什么 |
|---|---|---|
| 量结构 | `survey IMG.DNG` | 结构线位置、内容边界、可裁预算、方案表（**不打分**） |
| 量滚转 | `level IMG.DNG` | `roll_deg` / `confidence` / `vertical_spread` / `suggested_rotate` |
| 看候选 | `candidates IMG.DNG --crops-src "x,y,w,h;..." --annotate` | 一张标注拼图，每格带源坐标、比例、取景位置 |
| 出片 | `finish IMG.DNG --crop "x,y,w,h"` | `<stem>_final.jpg`，一条命令，无百 MB 中间稿 |
| 复核 | `compare 原图 成品` | 并排对比，确认真的裁了、没切坏 |

### 三个测量命令速览

```bash
P=scripts/photo_lab.py

python3 $P survey "IMG.DNG"          # 结构线 + 内容框 + 预算 + 方案表
python3 $P level  "IMG.DNG"          # Hough 竖边投票量滚转
python3 $P panels "IMG.DNG"          # N 张放大图合成一张，带源坐标刻度
python3 $P candidates "IMG.DNG" --crops-src "0,176,1068,1424;0,448,1068,1424" --annotate
python3 $P finish "IMG.DNG" --crop "0,448,2688,3584"
```

## 几个刻意的设计决定

**方案表不打分。** `survey` 只给 `area_removed` / `cuts_content_px` / `edge_penalty`，**没有总分、不排序**。因为"切掉天空 vs 切掉前景"没有可加的权重——那取决于你想保留什么。任何给出 87 分的裁剪工具，都在替你做一个它没资格做的判断。

**滚转必须两侧证据。** `level` 要求竖边横跨画面 ≥35% 宽度、且左右各有分布，否则一律返回 `roll_deg: null`、置信度 `low`。

> 这是踩坑换来的：某张外滩夜景，12 条"竖边"一致读到 −1.80°，看起来是压倒性证据。核查后发现 12 条全部落在 x 16–22% 的**同一面立面**上——同一面带壁柱的墙被检出了 12 次。仰拍高楼时那面墙的竖边本来就会倾斜，倾多少取决于它离光轴多远，这是 keystone，跟相机滚转无关。该图远场横线读 0.0°，真值是 0°。
>
> **"12/12 一致"这句话，在看到它们来自画面的同一个 6% 之前，是骗人的。**

**一致度要真多数。** `agree ≥ max(3, 40%)` 才算 `high`。3/12 是相对多数，不是共识。

**近景横线不判滚转。** 栏杆、马路牙子、江岸线是向远方收敛的 3D 线，成像必然斜，那个斜度是透视。它们只用来定位结构，不用来校水平。

**比例锁死意味着越界也不能改比例。** 裁剪框超出画面时，逐边 clamp 会悄悄改掉长宽比：1080×720 上请求 `900,0,600,400`（3:2），被夹成 180×400（1:2.2），命令还退出 0。正确做法是**先平移、平移不够再等比缩小**，两者都不动比例；只有完全在图外才报错。

**旋转按标准比例量化。** 内接框量化必须走 `nominal_ratio`（吸附到 4:3 / 3:2 等），不能用 `Fraction(w, h)`：800×533 互质，一个"比例单位"就是 800px 宽，比整个安全框还大，量化结果直接退回整帧，四个黑楔全留在成品里。

**不做调色。** 调色模块已从 v1.2.0 移除。Shore 讲"透明性"——结构是理解的表达，不是浇在内容上的酱汁。要胶片色调请接 darktable / Lightroom / SpektraLab。

**RAW 不落中间稿。** `finish` 用 `sips` 解码一次到私有临时目录，裁完直出，`finally` 删目录。对比 `raw-export` + `develop` 两步路：1.3s vs 6.8s + 107MB。

## 为什么有 `survey` 这个命令

第一版没有它。第一版的做法是：看缩略图 → 猜坐标 → 写一段 Pillow/numpy 代码量一下 → 再看。

复盘一次真实任务（单张竖幅）：**48 次工具调用、828 秒墙钟，其中工具自身只占 25.8 秒（3.1%）**。剩下 96.9% 是模型思考 + 每次调用重读上下文的成本。而这 48 次调用里，**47.5% 是临时手搓的测量脚本**，另有 19 次是重复看图。

结论很反直觉：**瓶颈不是算法，是往返次数。** 流程决定轮次，模型给每轮定价——单价改不了，乘数可以。

于是 v1.6.0 不优化像素算法，只砍轮次：测量全部命令化（`survey` 0.7s / `level` 0.7s / `panels` 0.6s），所有命令直读 RAW 并共享同一次解码缓存，候选框直接吃源坐标并回带 `finish --crop` 字符串。**轮次 48 → 8–14。**

## 已知限制

- **不做主体识别。** 锚点全部基于"主体大致居中"的几何假设，必须看图筛掉切断主体的方案。
- **`survey` 的方案表经常是空的，而且不能当成"不用裁"。** 采样器只在内容框之外的空白边距里找切点，内容占满整帧的街景一个方案都给不出（实测那张实际裁掉了 20%）。空的 `scenarios` 只说明采样器没找到，**不是照片的结论**；此时读 `structure_lines` / `clean_cuts` / `budget` 自己定切点。`verdict` 字段会说明空的原因。
- **RAW 解码是 macOS 专属。** 底层用系统 `sips`（ImageIO），Windows / Linux 上没有等价物，需要用相机或转换器先导出 JPEG/TIFF。非 RAW 格式不受影响。
- **竖幅可裁幅度天然小。** 竖幅的同比例内接框等于原框（`dx=dy=0`），能动多少完全由"必须留住的边界"决定，常常上下只能保一个。
- **`level` 在非建筑场景不可靠。** 地铁通道这类场景检到的"竖边"不是结构线，会给偏小的角度（实测 0.95° vs 真值 2.2°），此时置信度会降到 `medium`，应改用单线连续性追踪兜底。
- **广角仰拍的梯形变形旋转修不了。** 那是 keystone，旋转只会让另一头更歪。
- **XMP 兼容性未实测。** 本机无 Lightroom / ACR，`xmp-crop` 的输出需要你在自己的软件里核对一次。
